# 决策记录

每条都是"背景 → 决定 → 代价"。想知道现在为什么长这样、以及**改动它要付什么**，从这里找。

## 自研账号体系，不用 Supabase Auth

**背景**：使用者是校内几十人，需要用户名 + 密码、部门、管理员批量建号、停用即踢下线，且不希望引入邮箱验证流程。
**决定**：`app_users`（bcrypt cost 12）+ `app_sessions`（只存令牌 SHA-256 摘要，30 天）+ 自研登录/改密函数；`profiles` 表保留但只作为 `applications.owner_id` 的指向对象。
**代价**：口令策略、会话吊销、令牌熵都要自己负责；`profiles.email` 是历史占位（存的是用户名），与真实邮箱 `app_users.email` 并存，容易被误用。

## app-api 是唯一数据入口

**背景**：前端不能持有 service role key，而业务读写的可见范围（工作台、审计）无法用简单 RLS 策略表达。
**决定**：所有表对 `anon`/`authenticated` `revoke all`，前端只调 `POST {action}`；权限与规则在函数与数据库各再做一遍。
**代价**：多一跳；`index.ts` 体积大（600+ 行）；PostgREST 的直连便利（实时订阅、自动 REST）主动放弃了。

## 业务规则写在 PL/pgSQL 里

**背景**：状态机、门槛、"不能处理自己的申请"这类规则必须不可绕过。
**决定**：每个 `app_*` 函数第一行做权限与状态判定，用 `select … for update` 锁申请行；HTTP 层只做参数整形和错误翻译。
**代价**：规则分散在 TS 与 SQL 两处，必须靠测试盯住一致性（见 [testing.md](testing.md)）。

## 管理员不替代流程身份，内置 `admin` 例外

**背景**：早期"管理员可以干一切"导致职责混淆、审计分不清是谁在操作。
**决定**：`admin` 只管成员/配置/审计；财委、主席、付款登记是独立身份。唯一例外是用户名恰好为 `admin` 的内置超级管理员，且它的账号与角色被触发器锁死（不能改名、停用、删、改角色），连别的管理员也不能碰。
**代价**：小团队里"管理员顺手代审"不再可能；`cashier` 身份至今无法从界面分配，付款登记实际都落在内置超级管理员身上。

## 门槛用提交时的快照 `rule_threshold`

**背景**：主席门槛会被调整，流程中的申请不该被事后改动影响。
**决定**：提交时把 `settings.threshold` 写进该申请，审批去向按快照判断，`amount >= rule_threshold` 走主席（**恰好等于门槛要主席审批**）。
**代价**：管理员改门槛后，旧申请的详情页显示的是它自己的快照值，需要解释。

## 文件"草稿 → 显式提交"两步，且只替换不删除

**背景**：误选文件就推进状态造成返工；已提交的凭证是审计依据。
**决定**：`qr`/`receipt` 先落 `pending` 草稿，必须再调一次正式提交才改状态；替换时旧行打 `removed_at`，文件留在存储里；已提交凭证不许删除；存在未提交收款码草稿时禁止登记付款；移除已提交收款码会把付款挂回 `payment_info_required`。
**代价**：状态与文件组合的边界情况多（重复更换收款码、同一状态重复提交），是回归测试最密的地方。

## 通知只在"需要有人动手"时发

**背景**：最初设计是七类状态变化全发（含拒绝、已付款）。实际诉求是"轮到我做事时提醒我"，结果通知会变成噪音，还会让 QQ 发信账号撞风控。
**决定**：事件集收敛为五类——待财委审批、待主席审批、待付款登记（给对应身份，排除申请人）+ 退回修改、待补充收款码（给申请人本人）。拒绝、已付款、撤回、草稿**不发**。中途考虑过"管理员逐类勾选开关"（`settings.email_notify_events` 数组列），最终**否决**：事件集由"是否有待办"唯一决定，加一层配置只会让"为什么没收到"更难解释，也多一处三处不一致的来源。
**代价**：申请人不会被告知"你的报销已付款"，需要自己看站内；如果以后要，正确做法是加一个新事件而不是加开关。

## 队列用"带租约的原子领取"，语义是 at-least-once

**背景**：管理员手动点「立即发送」和定时任务可能同时跑；函数被墙钟超时打断会留下半批。
**决定**：`app_claim_notifications(批次号, 上限, 租约秒, 超龄小时)` 用 `FOR UPDATE SKIP LOCKED` 领取并写 `status='sending'` + `lease_expires_at`；写回必须同时匹配 `id` + `status='sending'` + `claim_id`；租约过期的 `sending` 行退回 `pending` 并计入一次尝试。
**代价**：崩溃在"已发出但未写回"窗口内的邮件会重发一次。选择宁可重复、不可漏发。

## 超龄提醒丢弃而不是无限积压

**背景**：开关关了一周再打开，会突然补发几天前的"待审批"邮件，收件人困惑且像故障。
**决定**：领取时把 `pending` 且超过 24 小时的行标记为 `failed`，原因写明"超过 24 小时未发送，已丢弃"。
**代价**：长时间不开邮件服务会真的丢通知；但站内状态始终是对的，队列里也留着丢弃记录。

## 事件名、审计事件名用中文，并且是数据契约

**背景**：界面、审计、邮件全部面向中文使用者，映射层只会增加错位机会。
**决定**：中文字符串直接进 check 约束、触发器 `CASE`、审计 `event` 列。
**代价**：改名等于改数据，需要迁移 + 四处同步 + 测试同步；这是仓库里最"重"的一类改动。

## 密钥只存在于运行环境

**决定**：邮件服务密钥、`CRON_SECRET`、SMTP 授权码全部走 Edge Function 环境变量或 compose 的 `.env`；pg_cron 的项目地址与密钥走数据库自定义参数 `stabx.email_cron_*`；仓库里既没有真实地址也没有长随机串（有测试断言）。
**代价**：换密钥要三处同步（函数 env、中继 env、cron env），流程写在 [deployment.md](deployment.md)。

## 邮件出口是 HTTP 接口，SMTP 交给自托管中继

**背景**：托管 Edge Functions 的官方出站限制只列了 `25` 与 `587`（[Limits](https://supabase.com/docs/guides/functions/limits)），`465` 并未禁止；社区也实测过在函数里用 denomailer 直连 465 发信（[supabase#21977](https://github.com/supabase/supabase/issues/21977)）。所以"函数发不了 SMTP"不是物理事实，只是未被承诺。
**决定**：函数这一侧**只**说 HTTP（`POST EMAIL_API_URL`，请求体 `{from,to,subject,html}`），SMTP 一律由 `deploy/mail-relay` 容器承担（`nodemailer` → `465` 隐式 TLS）。取舍的三条理由：465 直连属未承诺行为、且没有 587/STARTTLS 退路；`MAIL FROM` 必须等于认证账号的校验与 `RELAY_RATE_PER_MINUTE` 限频需要一个常驻进程来放；SMTP 授权码只留在中继容器，不进 Edge Function secrets。密钥因此分成两组：函数侧 `EMAIL_API_URL/KEY/FROM`、`APP_URL`、`CRON_SECRET`；中继侧 `SMTP_*`、`RELAY_TOKEN`（与 `EMAIL_API_KEY` 同值）。
**代价**：多一个要维护的容器（B 摆法）；纯云端部署必须选 HTTP API 型服务商（A 摆法）；用 QQ/单位邮箱/DirectMail 时绕不开一台能出 465 的机器。若日后要改成函数内直连 SMTP，先确认平台仍放行 465，再同步改测试与本文档。

## 去重键排除已作废的行

**背景**：去重按"版本 + 事件 + 收件人"，但工作流里有一个**不升版本**的状态重入：收款码被移除后重新提交（`payment_pending ↔ payment_info_required`）。原来的唯一约束会让第二次"待付款登记"提醒被静默吞掉——那是真实的待办，也是全系统唯一违反"宁可重复不可漏发"的地方。
**决定**：把唯一约束换成部分唯一索引 `where status <> 'cancelled'`；同时新增终态 `cancelled`。触发器在离开 `payment_pending` 回到 `payment_info_required` 时，把这一版的"待付款登记"提醒标为 `cancelled`（写清"收款信息已变更"，`sent_at` 保留），重新提交后自然能再入队一封。
**代价**：作废是就地改状态，已发出的那一封会从"已发送"计数挪到"已作废"（`sent_at` 仍在，能查出来）；管理面板多一类计数，`cancel` 不能与"发送失败"混为一谈——重置按钮只碰 `failed`。

## 发送前复核状态，过时的提醒作废而不是寄出

**背景**：入队与发送之间隔着 cron 周期、订阅开关、以及邮件服务故障时的退避重试（最长 24 小时）。这期间申请可能已经被处理、被撤回，或者换了收款人；不复核就会寄出"催办一件已经做完的事"，而且正文里的"当前状态"来自发送时刻，会和事件标题自相矛盾。
**决定**：`app-api` 维护"事件 → 仍然要处理的状态"映射（与数据库触发器的 `CASE` 逐项一致，测试比对两边），领取后发送前核对一次；不一致就标记 `cancelled` 并记录当时的状态。这是在"不寄无用邮件"与"不漏待办"之间选前者，因为状态已经变了就说明待办已由别人完成。
**代价**：多一次映射表要跟触发器同步（契约测试盯着）；已经在 HTTP 调用中的那一封挡不住（窗口 ≤15 秒，不为此加锁）。

## 限频与墙钟都按"暂停"处理，不消耗重试预算

**背景**：中继默认每分钟只放 12 封，应用侧却是每轮 100 封；429 原来和真失败走同一条路，`attempts` 每次 +1，几十分钟就能把正常积压打成"永久失败"。另外一轮最多 800 封，可能撞上托管 Edge Functions 的墙钟（150/400 秒）被硬杀，剩下的行停在 `sending`，等租约到期退回时还会再计一次尝试。
**决定**：429 视为限频——中继返回 `Retry-After`，app-api 暂停本轮、把被限频和同批没发送的行一起退回 `pending`，**不写 `attempts`**；一轮另有 240 秒时间预算，到点同样原样退回。真实错误（5xx、超时、网络）照旧消耗 5 次重试预算。积压让两层限频中的慢的那层决定吞吐，写进 [notifications.md](notifications.md#容量与频率)。
**代价**：积压大时发得慢（走自带中继约 12 封/5 分钟一轮），需要提吞吐就得放宽中继限频或换 HTTP 服务商；"暂停"路径多了一处状态写回，靠契约测试与 verify 脚本盯住。

## 定时消费优先主机 cron，pg_cron 只是可选便利

**背景**：自托管的 Postgres 镜像扩展集固定，pg_cron/pg_net 未必可用；而主机本来就有 cron。
**决定**：`send_notifications` 开放一个不依赖登录会话的入口（`x-app-cron` 恒定时间比较，且**只允许这一个动作**），主机 cron 一条 curl 即可；`20261005140000_email_notify_cron.sql` 存在但缺扩展或未配置时只打印提示并跳过。
**代价**：多一种调用路径，必须靠测试保证它没有被用来做别的事（`tests/email-notify.test.mjs` 断言登录前只放行这一个动作）。

## 导出在浏览器端完成

**决定**：函数分页取数（每页 1000、上限 10 万行）返回 JSON，前端用自带的极简 zip + CRC32 填 `public/export-templates/*.xlsx` 模板。
**代价**：模板要单独构建与校验（`scripts/build-export-templates.mjs`、`verify-export-workbooks.mjs`）；超过 10 万行必须缩小日期范围。

## 历史散装 SQL 保留原状，只加 fail-fast 前置检查

**背景**：把 `supabase/*.sql` 全部搬进 `migrations/` 会影响已部署库的迁移账本，属于独立的清理任务。
**决定**：暂不搬迁；新迁移在开头检查依赖的函数是否存在，缺了就立刻报错并指出该先执行哪个文件，同时把执行顺序写进 README 与文档。
**代价**：顺序知识仍然分散；重跑散装文件会重新引入 6 参数版 `app_admin_create_user`（PostgREST 用命名参数调用，不会静默丢掉 `p_email`，但这是需要知道的细节）。
